# 2026.331.0427 — fix(bed): prove the CDP capture's CONTENT and the VNC frame's FRESHNESS — and a real page

## Summary

Closes #2.

The pod's bed and its own skill claimed something false — and the false claim was the smaller half
of the find. `cdp: screenshot` was recorded as "uniformly white on every attempt" and therefore
asserted nothing; and the VNC frame was read as "what the streamed user sees" without any evidence
that the frame was FRESH. Both are fixed here, plus the real defect the second one exposed.

- **`charly.yml`** — `bed-cdp-screenshot-content` OCRs the CDP artifact and asserts the page's own
  text is in it (the "blank frame" was an assertion choosing 100 stride pixels and calling a
  mostly-white page uniform). The VNC-frame assertion is now made over the pod's own **VNC session
  recorder** instead of a single capture, because one capture is not evidence of what a viewer sees:
  measured, a capture right after the browser's restart cycle can hold a complete but OLD frame while
  every metadata check passes. The recording is re-read as it grows (the engine's `eventually:`), and
  it now runs AFTER the pointer/keyboard steps so the recording cannot interfere with them. A REAL
  external page (`https://example.com/`) is proven end to end on the CDP surface: fetched through the
  pod's egress, its live copy asserted by title and body needles, captured with `cdp: screenshot` and
  read back by OCR.
- **`.agents/skills/kde-vnc-cdp/SKILL.md`** — the false "measured GPU-Wayland limit" for
  `cdp: screenshot` is replaced by what is true (bounded surface attempt plus a view fallback = a
  real capture; assert content or bytes, never `artifact_not_uniform` on a page); a new section
  "A capture can carry a STALE frame" states the measured stall table, the four premises and the
  two-capture rule, with the host OCR prerequisites and the egress requirement.
- **`AGENTS.md`** — one repo rule: a VNC-frame assertion needs its premises and the SECOND capture,
  pointing at the skill for the detail.

Nothing in the pod's runtime changes: no candy, service, port, image layer or schema moves. The
image is rebuilt only because the bed runs against a fresh build (R10).

### RCA of the probe (R1)

The external-page probe failed six live rounds. The last four looked like the same failure and were
not: each round removed one wrong premise, and the round that finally named the mechanism came from
changing the INSTRUMENT, not the assertion.

```
round 1  navigate newest tab + Page.bringToFront                       → frame: New Tab
round 2  open a NEW tab + visibilityState + activate the page's window  → frame: New Tab
round 3  + kdotool windowactivate on the window TITLED with the page    → frame: New Tab
round 4  + match windows by CLASS, close strays, one tab only          → frame: New Tab
round 5  + assert the session is not screen-locked                     → frame: New Tab
round 6  + renderer gate + compositor configure                        → frame: New Tab
```

**Mechanism (measured on a persistent deployment, not a torn-down bed).** After the supervised
browser's `stop → browser-open → chrome-restart` cycle, presentation STALLS:

| probe | stalled state | healthy state |
|---|---|---|
| KWin window title / geometry / desktop / active | `Example Domain`, `0,0 1920x1034`, active | same |
| CDP `title` / `text` / target list | `Example Domain`, live body, one page target | same |
| `Page.captureScreenshot` `fromSurface:true` | hangs | hangs (a platform quirk, plugin-cdp#14) |
| `Page.captureScreenshot` `fromSurface:false` | **HANGS** | returns a PNG instantly |
| first `vnc: screenshot` after the stall | complete, coherent OLD frame | current frame |
| the `vnc: screenshot` after that | current frame | current frame |

So every metadata check is true while the screen shows an arbitrarily old frame: the browser is
alive and titled with the page, the compositor has the window maximized, active and on the current
desktop — and the pixels are the *New Tab* page from before the navigation. A compositor-driven
configure (un-maximize → re-maximize, what a user does to a window that looks stuck) makes Chrome
re-allocate and commit; the renderer answers a view capture again ~15 s later; and the connection
that arrives right after that is still served the buffer the VNC server already held, while the
NEXT connection reads the fresh state.

**Missed control.** Every earlier round asserted the state of the BROWSER and the COMPOSITOR —
metadata that a stalled presentation leaves perfectly intact. Nothing asserted that the renderer was
producing frames, that the compositor had presented one, or that the captured buffer was newer than
the action under test. A capture is not evidence of what the screen shows unless its freshness is
established; "the frame is not uniform" and "the frame OCRs *something*" both pass on a stale frame.

**Root fix (in the diff).** Stop treating a single capture as evidence, and do not "fix" the
presentation by moving the window:

1. **Assert over a recording.** The pod's own VNC session recorder captures the stream continuously;
   the OCR reads the LAST COMPLETE FRAME of the growing `frames.mjpeg` and the engine's `eventually:`
   re-reads it (2 attempts / 10.2 s on the green run). That is what a viewer's stream is, and it
   converges when presentation recovers instead of pinning one instant.
2. **Drive first, record after.** Measured regression in this round: with the recorder running before
   the VNC click/typing steps, the typing never reached the page — so the recorder now runs after the
   driving steps (the run above has both green).
3. **Delete the compositor surgery.** It was measured to be worse than the problem: un-maximize +
   re-maximize unsticks the renderer but rewrites Chrome's normal bounds to 913x1034 (which silently
   moved the page out from under the desktop-centre click), minimize/restore does not unstick at all,
   and a no-op `windowmove` can cause the stall. None of it ships.
4. **The external page keeps its CDP proof and loses its VNC leg.** On the failing state the streamed
   frame stayed stale for 3m20s (19 re-reads); that is not a bound a gate may depend on. The page is
   proven fetched, live, drawn and OCR'd through CDP; the stall is filed as
   opencharly/pod-kde-vnc-cdp#4 with every measurement and the remaining candidates.

**Spike round (R12)** — every candidate measured on a live failing state:

```
(a) poll the one-shot capture for a non-uniform frame        rejected round 1 (uniform-but-real page)
(b) activate the tab / the window, by title                  metadata PASS, frame still stale (6 rounds)
(c) match windows by CLASS, close strays                     PASS, frame still stale
(d) assert the session is not screen-locked                  PASS, frame still stale
(e) renderer gate: view capture within 3s                    PASS (3 attempts / 15.5s), frame still stale
(f) gate + un-maximize/re-maximize + ONE capture             PASS gate, frame still stale
(g) … + capture TWICE, assert the second                     frame fresh — but the configure had broken
                                                             the geometry: 913x1034, click/typing missed
(h) per-axis MAXIMIZED_HORZ/VERT + enforced geometry         22 attempts, NOT maximized: 913x1034
(i) minimize/restore as the configure                        geometry kept, renderer STILL stalled
(j) windowactivate / windowmove as the configure             unstuck once; a move caused a stall
(k) assert over the VNC session RECORDING (eventually)       marker frame green in 10.2s  ← CHOSEN
(l) the same recording for the EXTERNAL page                 3m20s stale, 19 attempts → filed as #4
```

(k) is the winner: it needs no configuration of anything, cannot disturb input coordinates, and fails
honestly if the stream never shows the page. (l) is why the external page's VNC leg is out.

## Filed issues

- **`opencharly/plugin-vnc#7`** (filed earlier in this work, still open, non-blocking): the `vnc:`
  verb does not accept `artifact_contains_text:`, although it is a shared artifact modifier that
  `wl: screenshot` carries. This PR works around nothing — it OCRs the pulled PNG on the host,
  which is the documented host-side form — but the verb-side gap is named there.
- **`opencharly/pod-kde-nested#6`** (filed with this PR, non-blocking): the nested Plasma session
  arms Plasma's screen locker, so a session idle for ~4 minutes shows the greeter — measured while
  building this probe (`ScreenSaver.GetActive` → true; the captured frame is the lock screen;
  `SetActive false` returns success and does not clear it; killing the greeter respawns it with
  `--immediateLock`). The probe now ASSERTS the session is unlocked before it captures, so this bed
  fails loudly with that cause instead of an unexplained OCR mismatch; the prevention fix and its
  spike belong to the session owner.
- **`opencharly/pod-kde-vnc-cdp#4`** (filed with this PR, non-blocking): the browser's presentation
  stalls after the supervised restart cycle — metadata stays correct, the captured frame is stale.
  Carries the measured table (view capture HANGS while stalled), the four mitigation attempts and
  their outcomes, the 3m20s worst case, and the three remedy candidates that need their own spike.
- `opencharly/plugin-cdp#14` — **closed** in this work with the measurement above: the capture is
  not blank; the assertion was wrong. No new finding survives this change.
- The `cdp: close` tab-resolution defect found in this work was fixed in `plugin-cdp#15`; it never
